# 真实数据 ETF 验证 CLI 设计

## 1. 目标

在现有样例回测链路之外，新增一个可重复执行的真实数据验证入口，用固定时间窗运行第一个正式 ETF 基线策略，并输出可审计的验证结果。

这个入口服务于“模拟验证 -> 灰度 -> 小资金验证”的工程链路，不承担课程讲解职责，也不承担自动实盘职责。

## 2. 为什么单独做 CLI，而不是继续堆在 notebook 里

当前仓库已经有两条不同职责的线：

- course notebook：负责教学、解释、演示
- `src/ai_xquanty`：负责真实工程化研究与回测

真实数据验证属于第二条线。

如果继续放在 notebook 中，会有三个问题：

- 不利于重复执行和参数固定；
- 不利于后续接入灰度验证流程；
- 容易把课程实验和工程验证混成一套。

因此，这一步采用单独 CLI，而不是继续扩展 notebook。

## 3. 范围

### 3.1 本次要做

- 保留现有 sample backtest CLI 不变；
- 新增一个真实数据 ETF 验证 CLI 入口；
- 让回测引擎支持按策略名切换信号函数；
- 将 `etf_trend_filter` 接入真实回测链路；
- 将真实 ETF 日线数据标准化为现有引擎可消费的数据结构；
- 输出净值、成交、摘要指标和基线比较结果；
- 对真实数据下载结果做本地缓存，避免每次重新下载。

### 3.2 本次不做

- 自动实盘下单；
- 参数搜索或自动调参；
- 多策略编排平台；
- notebook 与 CLI 的双维护执行逻辑；
- 面向任意资产类别的泛化框架重构。

## 4. 成功标准

这一轮完成后，系统应当能够做到：

1. 使用固定窗口真实 ETF 数据运行一次完整回测；
2. 通过 CLI 明确选择策略，例如 `trend_filter`；
3. 输出可复核的结果文件，而不是只在终端打印；
4. 和一个朴素基线做对比；
5. 支持后续重复执行同一验证，而不是依赖临时手工步骤。

## 5. 设计选择

## 5.1 方案 A：新增独立真实验证 CLI（推荐）

形式示意：

```bash
ai-xquanty run-real-backtest \
  --strategy trend_filter \
  --start 2021-07-28 \
  --end 2026-07-27 \
  --symbols 510300.SS,510500.SS,159915.SZ,159949.SZ \
  --output-dir out/real_validation
```

优点：

- sample 与 real validation 边界清晰；
- 后续可直接复用于灰度验证；
- 参数显式、可复跑、可审计；
- 不会把课程演示逻辑带进工程入口。

缺点：

- 需要多一条 CLI 和少量配置逻辑；
- 需要补一层真实数据准备接口。

## 5.2 方案 B：只写临时脚本

优点：

- 初期最快；
- 改动最少。

缺点：

- 很快会变成一次性工具；
- 不利于重复验证；
- 不利于后续沉淀成稳定流程。

## 5.3 方案 C：直接扩展现有 sample CLI

优点：

- 入口数量少；
- 复用现有命令结构。

缺点：

- sample 数据验证与真实数据验证职责不同；
- 过早耦合会让 sample CLI 语义变脏；
- 后续维护更容易出现条件分支膨胀。

## 5.4 结论

采用方案 A。

即：保留 sample CLI 为最小稳定样例入口，新增独立 real validation CLI 作为真实研究验证入口。

## 6. 系统设计

### 6.1 CLI 层

新增真实数据回测命令，负责：

- 接收策略名；
- 接收固定时间窗；
- 接收 ETF 候选池；
- 接收输出目录；
- 接收是否刷新缓存等执行选项。

CLI 只做参数解析和流程编排，不直接实现交易逻辑。

### 6.2 配置层

现有 `BacktestConfig` 主要面向本地 sample 数据文件。

本次需要扩展为同时支持两类输入：

- sample data config
- real market data config

但扩展方式应保持简单，不做“大一统万能配置”。第一版只引入真实 ETF 验证所必需的字段：

- `start`
- `end`
- `symbols`
- `cache_dir`
- `initial_cash`
- `strategy_name`

### 6.3 数据准备层

新增一层真实数据准备逻辑，职责是：

- 下载指定 ETF 的历史日线；
- 固定窗口；
- 处理下载边界（例如 `end` 排他问题）；
- 标准化字段；
- 生成现有引擎能使用的：
  - `calendar`
  - `instruments`
  - `bars`
- 将结果保存到本地缓存目录。

本层必须显式失败，不能悄悄回退：

- 某个 symbol 下载为空；
- 日期窗口不完整；
- 关键价格列缺失；
- 非法价格值存在。

### 6.4 策略选择层

当前引擎将 `compute_etf_signals` 写死在回测循环里。

这次要改成策略名 -> 信号函数的显式映射。

第一版只支持两个策略名：

- `rotation`
- `trend_filter`

其中：

- `rotation` 保持现有样例行为不变；
- `trend_filter` 使用已经定义好的趋势过滤信号函数。

这里不引入插件式注册系统，也不引入复杂 class hierarchy。第一版用简单映射即可。

### 6.5 回测引擎层

引擎层继续负责：

- 周频调仓；
- 组合构建；
- 风控检查；
- 下一交易日成交模拟；
- 每日净值记录。

本次对引擎的主要修改是：

- 从“写死某个策略函数”改为“按配置选择策略函数”；
- 保持已有 sample 回测结果不回退；
- 为真实数据验证输出补充更有解释性的 summary 字段。

### 6.6 报告层

第一版输出只要求稳定、可复核，不追求花哨。

至少输出：

- `equity_curve`
- `fills`
- `summary`
- `baseline_comparison`

其中 `baseline_comparison` 至少包含：

- 策略最终收益；
- 基线最终收益；
- 超额收益；
- 策略最大回撤；
- 基线最大回撤；
- 成交次数。

## 7. 第一个真实验证策略定义

第一版正式验证策略固定为：

- 小型 ETF 池；
- 周频调仓；
- 趋势过滤优先；
- 相对收益排名其次；
- 不做参数扫描；
- 不做训练集上找最优值后再回测全样本。

推荐默认 ETF 池：

- `510300.SS`
- `510500.SS`
- `159915.SZ`
- `159949.SZ`

推荐默认时间窗：

- `start = 2021-07-28`
- `end = 2026-07-27`

如果未来调整窗口，也应作为显式 CLI 参数，而不是使用 `today`、`now()` 或省略截止日期。

## 8. 基线定义

真实验证不能只看策略自己的结果，必须和朴素基线比较。

第一版基线采用：

- 同一 ETF 池；
- 等权买入持有；
- 同一初始资金；
- 同一时间窗；
- 不做主动调仓。

这样可以回答一个更重要的问题：

“这套规则，是否真的比简单持有同一篮子 ETF 更好？”

## 9. 测试策略

### 9.1 单元测试

至少覆盖：

- 引擎能按 `strategy_name="trend_filter"` 选择正确策略；
- 真实数据准备结果能转换成合法 `MarketDataBundle`；
- 下载结果为空或价格非法时明确报错；
- 基线比较函数输出字段完整。

### 9.2 集成测试

至少覆盖：

- CLI 能成功执行真实数据验证命令；
- 输出目录中生成预期文件；
- sample CLI 仍然保持可用。

### 9.3 研究验证

至少检查：

- 是否跑赢基线；
- 最大回撤是否可接受；
- 成交次数是否过高；
- 结果是否具备重复执行的一致性。

## 10. 风险与约束

### 10.1 网络依赖

真实数据下载依赖外部网络和供应商可用性，因此必须有缓存；否则每次验证都容易受环境波动影响。

### 10.2 数据口径差异

真实数据与 sample 数据不同，常见会暴露：

- 缺失交易日；
- 价格异常；
- symbol 可用性差异；
- 复权口径差异。

因此数据准备层必须强校验，而不是假设数据天然干净。

### 10.3 过早泛化

这一步如果试图一步做到“任意策略、任意资产、任意供应商”，范围会立即失控。

本次只做：

- ETF
- 日线
- 周频调仓
- 两个策略名
- 一个真实验证 CLI

## 11. 后续衔接

完成本设计后，下一步应按下面顺序执行：

1. 写 implementation plan；
2. 先用 TDD 把 `trend_filter` 接进引擎；
3. 再补真实数据准备与 CLI；
4. 最后运行固定 5 年窗口的第一次正式验证。

到这一步为止，我们的目标不是“证明它一定赚钱”，而是：

- 建立一个可重复执行的真实研究验证入口；
- 用统一标准判断它值不值得进入灰度和小资金阶段。
